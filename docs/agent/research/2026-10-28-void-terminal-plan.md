## 1. Background & Problem

打造以原神「虚空终端」为意象的知识 Agent：覆盖任务、剧情、对话、装备、剧情道具、家具、书籍全文及源仓库中的其他可解释数据；能够检索原文、理解上下文、连贯回答并展示证据；提供现代流式聊天、明暗主题、国际化、移动端体验。

用户已确认：支持访客自带 API Key 与站点共享 Key 两种模式，默认自带 Key；采用 Docker 部署到服务器，优先数据完整与可控。具体服务器、资源规格与预算尚未确定。所有产品实现须等待用户审查方案。

仓库现状：本地只有 .git，尚无提交；GitHub API 确认 SoraYama/void-terminal 为 public，size=0，has_pages=false。这只说明仓库状态，不代表部署已经配置。

## 2. Root Cause / Approach

### 2.1 实际数据源与覆盖边界

主源建议 [DimbreathBot/AnimeGameData](https://github.com/DimbreathBot/AnimeGameData)，补充源建议 [theBowja/genshin-db](https://github.com/theBowja/genshin-db)。前者保留原始配置与文本，后者适合结构化百科与多语言实体名。旧 Dimbreath/AnimeGameData、Dimbreath/GenshinData 路径本次访问为 404，不能继续写入导入配置。

Readable 已见 15 个语言目录；TextMap 有普通、Medium 与特定语言分片，须建立文件发现清单。genshin-db 本次看到版本 5.2.14、提交前缀 49a6544，中文目录有 30 个分类，但没有 quests/books/furniture 分类，因此不能用它独立支撑完整剧情与书籍全文。

授权记录：genshin-db 仓库提供 MIT；主原始源本次 API license=null、根目录未见 LICENSE。代码许可不能自动代表游戏文本与图片的再分发许可。实现将把代码、来源清单、素材署名分开维护；配图优先原创生成，不把网上可访问当成可任意再分发的证明。公开仓库不直接提交大型原始数据转储或模型权重。

### 2.2 数据加工与版本策略

管线：固定上游 commit → 下载缓存 → schema 检查 → 文本解析与关系还原 → 分块 → 索引 → 质量验证 → 原子切换数据版本。

- 统一 Document、Entity、Relation、Chunk、SourceSnapshot；至少保留稳定 ID、类型、语言、源路径、JSON 指针或段落定位、源 commit、数据版本、内容 hash。
- 对话保存图结构与条件，不把互斥选项拼成连续发生的剧情。任务先后关系、时间线与叙述者信息缺失时保留未知。
- 分块按对话轮次、场景、书籍段落；子块用于召回，父块与邻接节点用于理解。保留游戏格式标记的原始值及清洗后的显示值；主角名和分支占位符不可随意抹平。
- 角色与组织别名、中英译名做映射；同名异物区分类型和 ID。整理源不覆盖主源证据，冲突记录在案。
- 初期建议 UI 简中/英文，重点建立中英文本索引，保存其他语言来源信息并提供后续构建开关；UI 翻译与语料翻译分开，缺失译文明确回退原文。
- 默认只采纳可核实的正式发布快照；测试服、未来内容、版本状态不明的记录进入隔离区，不直接进入在线回答。
- 更新按内容 hash 增量处理，但依赖图中受影响的父实体、章节、别名与向量也必须重建；删除记录与删除索引同步。
- 每次构建产出覆盖报告：发现/适配/解析失败/缺失文本/失联关系的数量与样本。未完成类别不能标成全量。
- 原始数据与大索引位于持久化卷或对象存储，不进入浏览器 bundle。上游不可用时继续服务最后一个通过验证的快照，保留可回滚版本。

### 2.3 Agent 与检索

推荐：中文分词全文检索 + 精确实体/别名匹配 + 多语言向量召回，融合排序后展开上下文。单纯向量相似度不适合专有名词精确查找；单纯关键词也难覆盖间接提问和跨文本考据。

一次回答的行为：

1. 结合最近对话识别意图、实体、语言与剧透设置，必要时生成少量检索改写。
2. 应用主动进行第一轮检索，按版本和剧透权限过滤；不给模型跳过证据的自由。
3. 融合关键词、实体、语义结果，去重并选取证据。
4. Agent 按需调用 search_lore、get_entity、read_source、expand_dialogue 等只读工具；初始最多 4 轮，限制总 token 与证据数量，实际参数由评测调整。
5. 将结论、引用与明确标记的推论流式输出；证据不足时说明缺口或询问所指角色/任务。跨任务推断不能被包装成原文明确记载。
6. 引用 ID 由检索层生成并校验。点击后可看原文、说话人、任务/卷次、邻接段落、来源版本及上游固定 commit 链接。

不需要先训练原神专用大模型。长上下文不替代检索，模型已有知识不是来源引用。源文本仅作为待理解资料，不能执行其中的指令。事实类、剧情梳理、跨文本考据、物品对比与多轮追问分别纳入评测。

向量化不要求访客再提供第二个 API Key：站点侧部署本地 embedding 模型。候选为轻量 [multilingual-e5-small](https://huggingface.co/intfloat/multilingual-e5-small) 与较重的 [BGE-M3](https://huggingface.co/BAAI/bge-m3)，用中英文剧情评测和机器资源决定最终选择。入库与查询必须使用同一模型、revision、归一化和输入格式。站点仍承担 embedding、数据库与带宽成本；本次未做全量导入、资源压测或效果实测。

数据库建议 PostgreSQL + [pgvector](https://github.com/pgvector/pgvector#hybrid-search)。中文全文字段先在应用层分词，维护游戏专名词典，再进行倒排检索；不要依赖默认英文配置。是否加入独立 reranker 由召回与排序误差决定，不预先增加一套重服务。

### 2.4 模型与两种 Key 模式

2026-10-28 官方文档核实：DeepSeek V4.1 Flash 的当前 API model ID 为 `deepseek-flash`，服务版本为 DeepSeek-V4.1-Flash-1017，OpenAI 兼容 base URL 为 `https://api.deepseek.com`。支持流式及工具调用。用户提到的 `deepseek-v4.1-flash` 用作展示名称理解，不直接假定为可调用 ID。[官方接入文档](https://api-docs.deepseek.com/) · [模型能力表](https://api-docs.deepseek.com/quick_start/pricing/) · [Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)

官方文档本次未找到公开 embedding endpoint，不能把 DeepSeek Key 同时视为向量服务 Key。未使用真实 Key 进行 API 联调，文档能力不等于该站点已验证可用。

| 模式 | 产品行为 | 密钥与额度处理 |
| --- | --- | --- |
| 默认：自带 Key | 设置面板输入、显示/隐藏、测试连接、清除；提示账单由访客承担 | 默认只存浏览器内存；调用时经本站后端转发，仅在请求中使用，不写数据库、日志或监控；不能声称 Key 永远不离开浏览器 |
| 可选：站点额度 | 运营者启用后才显示，用户明确选择使用 | Key 只放服务端环境变量；按会话与 IP 限速、请求 token 上限、并发限制、全站每日预算、预算耗尽停用；不在 BYOK 错误时静默切换并花费共享额度 |

首版不开放任意外部 base URL 代理。未来需要兼容网关时，由部署者设置允许列表。共享 Key 和所有 .env 私密值不能进入 public 仓库或客户端产物。会话历史建议默认存本机 IndexedDB，可删除或导出；不自动公开聊天。

普通查词优先低延迟生成设置，复杂考据提供深入查证入口；具体 thinking 参数与首字耗时在真实接口联调后决定，不展示内部思维链。

### 2.5 前端 UI 候选

三套视觉方案用于选择设计方向，不意味着首版同时维护三套皮肤。每套均提供 light/dark/system 三种主题状态。

| 方向 | 视觉语言与主体验 | 优点与取舍 |
| --- | --- | --- |
| A：虚空终端（推荐） | 深森林绿、翡翠、古金细线、叶脉纹样；对话为主，原文在侧 | 与名称和须弥意象最贴合；需控制纹样和金色比例，确保长文可读 |
| B：教令院藏书阁 | 羊皮纸暖白、墨绿、书籍目录与阅读栏，AI 帮助考据 | 适合原文阅读；首页更像数字图书馆，聊天入口需要明显 |
| C：星海旅志 | 午夜蓝、星图金线、原创幻想城景；轻量探索首页 | 更有提瓦特旅行感；插画集中在首页，聊天区降低装饰，移动端节制动效 |

最初建议为 A，但用户最终选择 C「星海旅志」。后续采用午夜蓝/星图/旅行探索方向，浅色为晨光白与雾蓝；不沿用 A 的绿色主视觉。产品名称仍为 void-terminal。

核心页面与布局：

- 新对话：欢迎语、输入框、4–6 个真实能力引导问题；未配置 Key 时仍可检索与阅读已收录原文，开始生成时再引导配置。
- 聊天：桌面左侧历史导航，中间约 720–800px 阅读区，右侧按需展开引用原文；引用折叠时对话居中。
- 原文库：任务、角色、装备/物品、家具、书籍及其他分类；搜索筛选、条目详情、相关关系、书籍卷次与原文阅读。
- 设置：Key、额度模式、主题、语言、回答偏好、剧透选项、历史清理。
- 数据说明：当前快照、类别覆盖、更新时间、已知缺口、来源与素材说明。

交互：真实 SSE 内容流、正在检索/查阅原文/生成回答状态、停止、重试、重新生成、编辑提问、复制答案、引用跳转。用户向上滚动时不强制拉到底；取消请求同步终止上游和工具工作；网络异常保留已接收文本并给出可控重试，不伪造断点续写。

移动端采用单列聊天；历史为抽屉，引用为底部面板或全屏阅读页；处理安全区和软键盘，操作目标至少 44px，横向表格有局部滚动。支持键盘焦点、可读对比度、屏幕阅读器状态通知与 prefers-reduced-motion。标题可用有授权的宋体/衬线，正文用清晰无衬线，中文字体按需加载。

国际化建议首版简中与英文；界面语言、回答语言、原文语言是三个独立设置。切换语言不丢失历史、不把自动翻译冒充游戏官方译文。

剧透建议首版提供「全部已发布内容」与「指定版本上限」两档。无法确定版本的内容在限制模式下保守排除；过滤同时覆盖检索、历史上下文、缓存和建议追问，仅在输出端遮罩不足。细粒度按玩家任务进度过滤属于后续能力，需可靠的任务进度元数据；首版不承诺绝不剧透。

流式事件计划包括检索进度、来源清单、文本增量、完成、错误及取消。断连保留部分回答并标记未完成；停止不能撤销已经发生的上游用量。BYOK 同样不得写入追踪、错误上报或缓存。

### 2.6 技术架构与部署备选

推荐应用结构：Next.js / React / TypeScript 提供页面、聊天与 Agent 流式 API；Python 提供离线解析、索引构建和 embedding 服务；PostgreSQL + pgvector 保存资料、关系、倒排与向量索引。UI 使用可复用组件和语义化设计变量，字体、颜色、间距与动效统一管理。

数据流：GitHub 固定快照 → 离线导入 → 文本/实体/关系库 + 检索索引；用户问题 → 服务端检索 → DeepSeek（必要时追加只读工具）→ SSE 答案与引用 → 浏览器原文面板。

| 部署方式 | 适合情况 | 需要承担的工作 |
| --- | --- | --- |
| A：Docker Compose（推荐） | 单机部署、完整语料、自托管 embedding、维护少量服务 | 服务器、持久化卷、TLS、备份、监控、模型初次下载；硬件建议在样本与全量基准后确定 |
| B：Vercel Web + 独立检索/embedding + 托管 PostgreSQL | 希望 GitHub 关联预览部署、托管数据库 | 多服务配置和账单；大规模导入、模型加载不放 Vercel 请求函数内 |
| C：GitHub Pages 前端 + 外部 API | 必须使用 github.io 域名 | 需要静态导出前端并把全部后端功能外置；它仍不是纯静态全量 Agent |

GitHub public 仓库可以接自动部署，但 Pages 本身只提供静态站点托管。[GitHub Pages 官方说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages) Next.js 可自托管，代理链需要保证流式响应不被缓冲。[Next.js 自托管文档](https://nextjs.org/docs/app/guides/self-hosting)

纯 GitHub Pages + 浏览器下载全部语料/索引 + 直连模型，不作为完整需求的推荐方案：大规模加载、模型 CORS、共享 Key 与后台更新均存在限制。用户已选择 Docker 服务器部署；其余方式仅保留为备选比较，不作为并行交付要求。

CI 建议区分代码发布与数据发布：代码检查/构建/预览；数据上游检查/增量构建/质量报告/原子提升。数据流水线异常不替换在线可用版本。具体定时任务在实现获批后落地，不在本次调研中创建。

### 3.1 获批后的实施顺序与验收

| 阶段 | 产物 | 验收重点 |
| --- | --- | --- |
| 0：方向确定 | 用户选定 UI、部署与语言/剧透范围；形成最终设计规格和实施计划 | 用户明确批准后才开始产品编码 |
| 1：数据基础 | 固定源清单、解析器、关联模型、代表性样本、覆盖报告 | 至少验证任务分支/说话人、武器故事、圣遗物套装、家具、书籍卷次与正文；失败可定位 |
| 2：检索与证据 | 全文+实体+向量混合检索，原文定位工具、评测集 | 精确专名、别名、间接表述、中英名称、跨文本问题、空结果均可验证 |
| 3：Agent 链路 | DeepSeek 流式、有限工具循环、引用、两种 Key 模式 | 真实 API 端到端；无效 Key/429/超时/停止/重试/额度耗尽均有正确行为 |
| 4：完整站点 | 获批视觉方向、聊天、文库、原文阅读、设置、主题/i18n/移动端 | 桌面与移动浏览器真实操作，深浅色与语言切换无布局问题，引用点击可读 |
| 5：完整语料与发布 | 所选正式快照中各目标类全量导入、增量更新、部署配置、说明与回滚 | 不以小样本作为全量完成；全量覆盖报告、性能基准、在线真实访问与问答验证 |

拟议质量门槛（目标，非已取得结果）：

- 建立至少 80 个固定评测问题，覆盖任务/对话、装备道具家具、书籍与跨文本、多轮、中英及不存在内容；答案依据来自固定原文。
- 对可回答的有标注问题，正确证据 Recall@10 目标 ≥90%；引用定位可解析率 100%，逐主张人工抽查证据支持率目标 ≥95%。样本量与类型分布在导入后补齐。
- 对话图不制造环路顺序或互斥剧情，书籍片段能返回正确卷次与上下文；无法判定的记录须在报告中出现。
- 断连/取消后不继续无限调用；共享额度限额有并发安全的服务端约束；构建物和日志不包含 API Key。
- UI 验证 360px、390px、768px 与桌面，暗/亮/系统主题、中文/英文、长回答、长引用和软键盘场景。
- 分别测量页面加载、检索耗时、首个内容 token、总回答耗时、内存/磁盘与每次回答 token；网络和模型耗时单独记录，不承诺固定首字时间。

## 4. Conclusions / Lessons

- 必须同时使用原始剧情/全文源与整理百科源；有角色属性并不意味着有任务剧情全文。
- 数据量、资源消耗、分支完整性尚未实测，不能预先宣称全版本、全语言、全剧情均完整。
- model ID 已核实，真实 Key 联调仍属于后续实施；一个 DeepSeek Key 不自动提供 embedding 服务。
- 两种 Key 模式、Docker 部署、C「星海旅志」和总体设计已获同意；先审查高保真前端视觉稿，再进入产品编码。真实服务器发布尚未执行。
- 概念图仅供视觉选择，其中书名、示例文字、页码不代表真实游戏原文或真实检索结果。
