# Hosted email-code login and trial credits

The official site runs with `DEPLOYMENT_MODE=hosted`: email-code login and account credits are its only model-access path. It has no BYOK settings, custom provider/model controls or mode switch. Operator-owned model calls require a verified email account. Missing authentication, model or budget configuration denies generation; it never falls back to BYOK. There is no checkout, subscription or cash balance.

The same open-source codebase and Web image default to `DEPLOYMENT_MODE=self-hosted`, which uses browser-supplied model keys without account UI or any Supabase/SMTP dependency. Self-hosted ignores the server model key and account/shared flags. The variable is read at runtime: only an absent variable defaults to `self-hosted`; an empty or unknown value is a configuration error and fails closed. Recreate the Web container after changing it; a separate mode-specific image build is unnecessary.

For the first hosted setup, follow the [Supabase + Resend onboarding guide](account-trial-onboarding.md) for provider setup, together with the current runtime configuration below. That guide also records the earlier onboarding acceptance; it is not proof that a new deployment is configured or healthy.

## Enable after local acceptance

1. Create a Supabase project and configure email authentication with a production SMTP sender. In both the **Confirm sign up** and **Magic Link / OTP** email templates, include `{{ .Token }}` as the code instead of requiring the user to follow a link. Keep the email OTP length at six digits (matching this UI) and set an appropriate short OTP expiry and provider email/verification rate limits. The site uses the official Supabase server SDK; no browser auth SDK or token storage is used.
2. Set `DEPLOYMENT_MODE=hosted` on Web. Configure `SUPABASE_URL` (HTTPS project origin), `SUPABASE_PUBLISHABLE_KEY` (`sb_publishable_...`, never secret/service-role), `PUBLIC_APP_ORIGIN` (exact public HTTPS origin), and `TRIAL_ALLOWED_EMAILS` (comma-separated invited emails). Use `*` only when intentionally opening public trials. Allowlisting is rechecked on every server session verification, including existing sessions. Local `npm dev` also requires an explicit browser origin, such as `http://127.0.0.1:3000`; a production Docker container requires HTTPS.
3. Set `ACCOUNT_TRIAL_ENABLED=true` for web AND knowledge. Set `ACCOUNT_TRIAL_CREDITS=20` on knowledge (new-account grant only). Set `SHARED_MODE_ENABLED=true`, `DEEPSEEK_API_KEY`, a random `SESSION_SECRET` of at least 32 characters, and `KNOWLEDGE_API_TOKEN`. Keep the operator key and internal token server-side. Set a finite positive `SHARED_DAILY_TOKEN_BUDGET`; zero denies generation. This cap reserves worst-case tokens for up to five model calls, so very small limits may reject all questions. `SHARED_MODE_ENABLED` is an operator gate for hosted account usage, not a user-selectable mode.
4. Compose stores the ledger in the independent named `accounts` volume at `/accounts/accounts.sqlite`, regardless of corpus backend. For local knowledge processes, explicitly set `ACCOUNT_DATABASE_PATH` to an absolute, writable file outside all corpus/snapshot directories. Do not copy this ledger into immutable corpus archives. This first version requires one knowledge instance and a local filesystem, not replicas with separate ledgers or NFS.
5. Deploy web and knowledge together, then verify `/api/status.deployment.mode` is `hosted` and the browser shows account/credit controls without Key/provider settings. Check invited login mail, invalid/expired code, logout, repeated login (no new grant), one standard/deep query, cancellation, exhausted credits and account isolation. Hosted chat/model-test routes must reject BYOK even when an old browser preference or a direct API request supplies it. Real email and generation checks require SMTP/Supabase credentials and authorized model calls; automated fixtures cannot establish delivery or real provider acceptance.

Both Compose files pass these variables at runtime and mount the same independent ledger path. SQLite and PostgreSQL are choices for the corpus; neither changes the ledger backend or removes the single-knowledge-instance constraint. SMTP credentials are configured in Supabase's auth sender settings, not as browser variables or model-provider credentials.

Official setup references: [Supabase email OTP](https://supabase.com/docs/guides/auth/auth-email-passwordless), [server client and session verification](https://supabase.com/docs/guides/auth/server-side/creating-a-client).

## Upgrade an existing hosted deployment

Before starting the new image, add **`DEPLOYMENT_MODE=hosted`** to the existing production environment. Do not overwrite `.env` with the example file: deployments without the explicit mode now default to self-hosted. Retain the existing authentication/model configuration, Compose project name, `accounts` volume and `/accounts/accounts.sqlite` path.

Record the previous commit/image and back up the account ledger separately from the corpus. The credit-foundation release upgrades legacy ledgers to schema v2 when the knowledge service opens them. Stop all account writers and follow the [ledger migration and recovery procedure](credit-ledger.md) before starting that image; old binaries reject the v2 tables. Recreate Web with the runtime variable, verify mode and UI, then check the existing account balance and history metadata. Retain the original account volume and migration backup; a code rollback across this schema boundary requires a separately verified recovery decision, not an in-place database overwrite. Changing the deployment mode itself does not migrate or erase balances or browser histories. An invalid mode must fail closed, while a hosted dependency outage must stay hosted and report unavailable.

## Credit semantics

- Standard research consumes 1 credit; deep research consumes 3. A new account gets the configured gift once. Trial and operator grants are non-cash credits. Real payment collection is not enabled.
- Schema v2 records every initial, legacy, manual or internal payment grant separately and checks that their sum matches the account total. Manual grants require the operator CLI and a stable UUID reference; exact retries do not issue credits twice. The account panel shows the latest 20 incoming grants separately from research usage, without internal references or operator reasons.
- Admission atomically reserves credits and allows one active request per account. Request IDs are never replayed, including after failure. A fresh explicit retry must use a new UUID.
- Successful model answers consume the hold. Failed, cancelled and no-evidence runs release it. Account settlement retries once independently of browser cancellation. If the process or ledger is unavailable, holds expire after 10 minutes and are released on the next ledger operation; the agent has a 180-second deadline.
- Operator global token budget is separate: unknown provider usage conservatively retains its reservation. User trial credits are fixed units, not a monetary estimate or token invoice. A failed request can still incur operator model cost.
- Usage history keeps the latest 20 request metadata records visible: request ID, timestamp, depth, model, units, status and aggregate provider tokens when known. It does not store prompts, answers, email addresses or provider keys. Aggregate tokens cannot be used as an exact invoice because provider caching and pricing categories differ.

## Privacy and operation

Supabase processes login email and authentication data. The application verifies each session server-side and uses HttpOnly, same-site cookies. The application and configured model provider process questions and evidence needed to answer. Do not claim that the server cannot read user questions. The browser stores chat history per account on that device, separately from self-hosted guest history. An identity outage must not expose guest or another user's history. This is UI isolation, not encryption against someone with browser-profile access. Clearing site storage deletes local chats. Login does not sync history between devices.

Use the [dedicated ledger CLI](credit-ledger.md) to create an online SQLite backup, verify it and rehearse restore to a fresh target. Stop account writers for migration or live recovery. The repository's `scripts/backup.sh` and `scripts/restore.sh` cover PostgreSQL corpus data and sources, not the `accounts` volume. Do not reset balances by deleting the volume, and do not run `docker compose down -v` as routine deployment. Retain the original volume on rollback and respect schema compatibility. Disabling account/shared access in a hosted deployment preserves credits and history metadata but makes account generation unavailable; BYOK stays disabled.

Auth endpoint in-memory limits protect a single web instance; Supabase provider limits remain necessary. Public signup also needs abuse controls and a measured operating budget before opening `TRIAL_ALLOWED_EMAILS=*`. The internal order/payment core now provides atomic, idempotent credit issuance, but has no public payment endpoint. Stripe Checkout, signature verification, provider reconciliation, refunds/disputes, durable research settlement and product terms must be implemented and accepted before real collection; see the [Stripe follow-up boundary](credit-ledger.md#stripe-follow-up).
