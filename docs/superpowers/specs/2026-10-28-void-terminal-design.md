# void-terminal 最终设计评审稿

日期：2026-10-28。状态：用户已批准总体方案及采用官方须弥素材的 v2 视觉稿，并明确要求继续；目前进入实现、全量语料导入与验收阶段。生产服务器尚未提供。

## 1. 目标与已确认决定

做一个以原神「虚空终端」为命名来源、以星空与旅行探索为视觉主题的百科 Agent。用户能够直接提问、连贯追问，也能够阅读任务对话、装备故事和书籍原文，并核对答案依据。

用户已确认：

- UI 选择 C 的探索与旅行结构，但 v1 自创写实海港被用户否定；改为采用原神自身 Logo、官方风景与动画美术质感。产品名称仍为 void-terminal／虚空终端，「星海旅志」不是改名。
- Docker 部署到服务器，优先数据完整与可控。
- 同时支持访客自带 Key 与站点共享 Key，默认访客自带 Key。
- 总体方案已获同意；先交付并审查前端概念图/设计稿，再进入产品编码。

随总体方案采用的默认值：首版界面与重点语料索引支持简中、英文；聊天历史保存在本机；无登录要求；优先原文问答、剧情梳理与百科查询；首版不包含语音交互、账号角色同步、多人协作或战斗模拟器。数据范围不因这些交互取舍而缩减为演示样本。

## 2. 方案比较与选择

| 议题 | 备选与取舍 | 最终方向 |
| --- | --- | --- |
| 视觉 | A 须弥深绿更贴近终端；B 藏书阁利于阅读；C 星海更突出旅行探索 | 用户选择 C；长文区保持低装饰和清晰阅读，不沿用 A 的绿色主色 |
| 部署 | Docker 对数据与 embedding 可控；托管组合减少部分运维但增加服务配置；Pages 仍需外部 API | 用户选择 Docker；首版交付一套可复现运行环境 |
| 检索 | 全文精确但怕转述；纯向量容易忽略专名和条件；混合检索兼顾两者 | 建议全文、实体、向量融合，关系与上下文展开 |
| 模型 | 直接用模型记忆无法给出可靠原文证据；训练专用模型增加数据与运维成本 | 建议 DeepSeek V4.1 Flash 加 RAG 与只读工具 |

调研依据、具体源表及来源链接见 [研究记录](../../agent/research/2026-10-28-void-terminal-plan.md)。

## 3. 页面与视觉设计

### 3.1 视觉规则

按用户修订后的 v2：深色采用深灰蓝背景、灰蓝面板、奶油白正文与柔和金色；浅色采用温润米白、灰蓝操作色与少量金色分隔。须弥官方场景和原神 Logo 在两种主题中保持辨识，重点是游戏菜单的轻盈感，不延续 v1 的写实史诗装饰。

颜色最终以 v2 画面和实际对比度校准，避免固守 v1 的近黑夜蓝起点。字体、颜色、间距、圆角与动效使用统一语义 token；浅色底、暗色底和控件必须按主题成组定义，不逐页硬编码。

用户要求使用原神自己的素材，避免 v1 类中土世界的写实风。首页采用来自官网的原神场景，优先须弥，保留原游戏的建筑、植被、地形与动画渲染；允许使用原神 Logo 作为 IP 标识，同时保留 void-terminal 品牌与非官方知识站说明。输入区使用稳定底色，进入聊天后收起大型场景。减少繁复星轨与厚金框，采用游戏菜单感的米白、灰蓝与柔和金色；正文与控件为清晰无衬线。不用自动播放声音，尊重减少动态效果设置。

[三套概念对照图，采用右侧 C](../../design/concepts/2026-10-28-ui-directions.png)。图内书名、页码、回答为占位，不会直接进入真实产品数据。

选定 C 后已制作[高保真页面稿 v1](../../design/star-voyage-v1/README.md)，但用户认为过于写实。用户现已批准[原神素材修订 v2 四张页面稿](../../design/genshin-v2/README.md)，实现和视觉验收以 v2 为准；v1 仅保留设计历史。

### 3.2 页面构成

| 页面 | 核心内容与行为 |
| --- | --- |
| 探索首页 / 新对话 | 星空与城景、明确的提问框、角色故事/任务脉络/书籍考据等入口；进入即可打字，不先弹出强制配置窗口 |
| 聊天 | 历史导航、消息流、引用原文面板；停止、重试、重新生成、编辑提问、复制和导出 |
| 原文库 | 任务、角色、装备/道具、家具、书籍、其他；类型与语言筛选、关键词搜索 |
| 条目与原文详情 | 属性、故事、相关实体；任务对话分支、书籍卷次与段落；从选中文本发起提问 |
| 设置 | API Key 测试/清除、额度模式、主题、语言、回答偏好、历史清理 |
| 数据说明 | 活跃数据快照、各类覆盖、更新日期、缺失与解析问题、来源和素材说明 |

未提供 Key 时仍可搜索和读原文；只有开始模型生成才引导输入 Key 或选择已开放的站点额度。首版不提供文件上传，避免概念图中的装饰图标被误认为已支持上传检索。

### 3.3 布局与交互状态

桌面左导航约 240px，中间正文最大宽度约 760px，引用面板约 360px 按需展开。平板折叠导航，空间不足时引用以覆盖面板展示。手机单列布局，顶部导航入口、底部输入框，引用用底部面板或全屏阅读页；处理软键盘与安全区，触摸目标至少 44px。

必须覆盖空白、检索中、生成中、已停止、未完成、错误、无结果、缺译文、无额度等状态。用户向上阅读时不强制滚到底；显示回到底部入口。编辑旧问题时从该位置重新生成后续分支，本机保留旧分支并允许切换；不把旧回答误接到新问题后。

明暗主题支持 light/dark/system；首访跟随系统。语言切换不丢历史，回答可随界面语言或单独指定。原文始终保留来源语言，模型翻译明确标记为翻译。键盘操作、焦点、对比度、屏幕阅读器与减少动态效果纳入验收。

## 4. 数据范围与管线

主源 DimbreathBot/AnimeGameData，补充源 theBowja/genshin-db；固定 repo、commit 与文件清单。首个拟评估快照为研究中已核实的 CNRELWin7.1.0 提交，实施开始时重新检查源状态并固定实际使用版本；不直接追随浮动 main。

目标覆盖源快照中可获得的任务、剧情、对话、武器、圣遗物、材料、剧情道具、家具、书籍全文、角色故事/语音、怪物、食物、成就、七圣等其他文本。全部目录都需盘点；纯运行配置、缺失上游正文、未知字段与未适配类型分别列出。未完成适配不算全量验收通过，用户要求的主要类别不能仅用样例代替。

输入 → 缓存固定快照 → schema 检查 → 提取原文与结构 → 关联实体 → 分块 → 构建全文和向量索引 → 校验报告 → 原子发布。

数据对象至少包括：SourceSnapshot、Entity、Document、DialogueNode/Edge、Relation、Chunk、EmbeddingManifest。共同字段包含来源 ID、类型、语言、repo/commit/path、JSON 指针或段落定位、内容 hash、快照 ID。

- 原始与清洗文本并存；保留旅行者名字、性别选项和动态占位的可逆表示。
- 任务与对话保留角色、选项、后继边和条件，不把互斥路线拼成线性剧情；循环、孤立节点与未知关系有显式状态。
- 书籍关联系列、卷次、章节与正文；属性介绍、获得方式和正文不混淆。
- 按真实实体 ID 对齐中英名称与别名，不只按字符串合并同名项。
- 按语义边界切块，保留父文档、邻接段落和分支信息；长书不整本塞入模型上下文。
- 所有语言列入来源清单；首版实际完整构建中英索引，其他语言作为可配置构建扩展，不宣称已具备所有语言回答质量。
- 正式客户端快照与测试服来源分开；首版不主动采集测试服源。正式客户端中未开放内容若可识别则隔离，无法可靠判定时明确边界，不保证源快照等于所有内容都已对玩家开放。

增量构建处理新增、修改和删除；内容 hash 未变可复用 embedding，受影响的章节、关系与别名同步重建。新快照校验失败不切换线上。每次会话固定一个快照；新数据发布后新会话使用新快照，旧引用仍可解析。默认不自动清理已发布快照的原文、定位和 manifest，相同内容按 hash 复用；避免仅保留上一个回滚版本而破坏更早会话的引用。保留成本纳入磁盘测量，未来清理策略须显式说明对旧会话的影响。

## 5. 检索、生成与引用

一次用户请求首先检索，而后生成。检索链为：问题和多轮指代处理 → 实体/别名匹配 + 中文分词全文 + 多语言向量 → 融合排序 → 去重 → 上下文与关系展开。初始不引入独立知识图数据库，关系保存在 PostgreSQL。

工具包括 search_lore、get_entity、read_source、expand_dialogue。默认最多 4 轮追加工具调用，限制片段数、总上下文、输出 token 和超时。原文里的指令仅视为文本，不执行网页或源文件中的操作指示。

回答先给结论，再按需解释，显示可点击引用；明确区分原文事实、综合推论、资料冲突与无证据。来源 ID 由检索服务颁发，模型不能创造新的有效来源。点击能回到具体说话人/任务节点/书籍卷次/段落，并能访问上游固定 commit。定位校验和事实支持评测分别执行。

站点侧使用本地 multilingual-e5-small 作为首个 embedding 基准候选；若中英评测未达门槛，比较 BGE-M3 后根据效果与资源选定。最终 model revision、预处理、归一化、向量维度和索引参数写入 manifest，入库与查询严格一致。该选择交由实现者基于证据完成，不要求访客提供 embedding Key。

剧透控制首版以可验证快照为基础：默认查询当前收录快照；只有存在并通过校验的历史快照时，才允许选择更早版本范围。没有对应快照就明确不可用，不从最新文本猜测旧版本内容。范围约束同时作用于检索、历史上下文、缓存和建议追问。玩家个人任务进度过滤留待以后，首版不承诺绝不剧透。

## 6. 模型、Key 与流式协议

使用 DeepSeek 官方 OpenAI 兼容接口，base URL 为 https://api.deepseek.com，当前模型 ID 为 deepseek-flash，UI 显示 DeepSeek V4.1 Flash。首次真实联调核验可用性与能力，不把展示名称当任意 API ID。普通问答优先低延迟参数，深入考据允许更充分查阅；具体参数由联调决定。

BYOK 默认仅保存在当前页面内存，刷新后需重填。用户 Key 请求时经本站后端发送给 DeepSeek；不进入数据库、日志、监控、错误上报或缓存。不提供任意 base URL 代理。会话、消息与引用保存本机 IndexedDB，可删除和导出，不默认同步到服务器或公开。

共享模式默认关闭，配置服务端 Key 与额度后才开放；访客明确选择，BYOK 失败不自动切换。共享 Key 不进入前端 bundle、Git 或镜像层。以签名匿名会话与可信代理下的 IP 做限速，并用数据库事务实现并发安全的全局预算预留与结算；未知用量保守计入预算，不靠客户端控制用量。

SSE 事件含 status、sources、text_delta、done、error；取消由客户端 abort 传递到后端并终止未完成上游/工具请求。心跳维持连接，反向代理禁用响应缓冲。断连或取消保留已收到文本并标记未完成，重试是新请求，不伪称能精确接着原流恢复；已经发生的上游用量不能撤销。

## 7. Docker 架构与运行

| 服务 | 职责 | 暴露范围 |
| --- | --- | --- |
| web：Next.js + TypeScript | 页面、Agent 编排、Key 代理、SSE、限额入口 | 经 TLS 反向代理对外 |
| knowledge：Python + FastAPI | 检索、上下文、只读来源接口、常驻 embedding 模型 | Docker 内网 |
| postgres：PostgreSQL + pgvector | 原文、实体、关系、全文/向量索引、快照与预算 | Docker 内网，持久化卷 |
| ingest：与 knowledge 共用代码的作业命令 | 下载、解析、增量构建、验证、快照发布 | Compose 作业 profile，非每次提问执行 |

生产入口提供反向代理配置；允许复用已有 TLS 代理。原始数据、模型缓存、数据库和备份使用持久化卷，不能塞入普通 Git 历史或应用镜像。首次模型下载与导入在部署步骤中显式执行；首次无数据时显示初始化状态，不用假回答冒充已接好语料。

GitHub Actions 执行代码检查、构建和镜像生成；生产部署、数据更新分别提供明确的命令与配置入口。数据发布采取 build → validate → activate，并保留上一有效版本。未配置部署凭据前不连接或修改真实服务器。

提供 .env.example、Compose、初始化/更新/备份/恢复说明与健康检查。实际服务器、域名与预算暂未提供；这些影响最终上线，但不阻止获批后本地实现。先测量全量磁盘、峰值内存、构建耗时、查询并发，再给硬件建议；不预先承诺免费或某台小机器一定够用。

## 8. 实施顺序与验收

本节是用户评审所需的交付顺序。设计获批后将生成文件级实施计划，再开始代码工作。

1. 数据与契约：固定源、解析各主要类别、定义引用与覆盖清单；先做代表样本验证，再完成全量适配。
2. 检索与评测：建立中英实体词典、全文与向量融合、上下文工具；冻结基准与门槛后优化。
3. Agent 端到端：真实 DeepSeek 流式、多轮、证据、取消/错误及双 Key 模式。
4. C 方向站点：完成首页、聊天、文库、原文阅读、设置；暗/亮主题、国际化、移动端。
5. 全量与上线：目标快照全量索引、资源测量、更新与回滚；Docker 运行验证和获授权的服务器部署。

验收目标：

- 至少 80 个固定问题覆盖各主要内容类、分支剧情、跨文本、中英、多轮、错误前提、资料缺失。所有答案依据可人工核对。
- 可回答样本的证据 Recall@10 ≥90%；引用定位可解析率 100%；逐主张抽查证据支持率 ≥95%。这是目标，不是已有成绩。80 题按类别公布分布，不用纯实体查词稀释复杂问题。
- 每个主要类别全量处理完成；缺失正文、混淆字段、悬空关系、未适配表逐项汇报，不能用少量样例宣布完成。
- 真正停止请求；无效 Key、429、超时、断连、限额和预算并发测试通过；构建物与日志检查无 Key。
- 验证 360px、390px、768px 与桌面，长回答、引用阅读、软键盘、中英切换、深浅主题和键盘操作。
- 单独报告页面加载、检索、首个内容 token、完整回答延迟、服务资源、单问 token；模型与网络耗时不能伪装成本站性能。
- Docker 从文档可重复启动，原文引用经数据更新仍可访问，备份恢复和数据回滚可验证。生产访问与本地验证分开记录。

## 9. 交由实现者的选择与批准范围

不再要求用户决定具体组件库、分块 token 数、融合权重、模型量化方式、代码目录细节；实现者根据当前兼容性与基准选择并记录。默认不引入 Redis、独立图数据库或复杂 Agent 框架，除非出现明确需求证据。

项目代码许可建议 MIT，保留数据与素材各自来源说明，不把代码许可套用到游戏文本。源文件和内容权属记录属于交付的一部分，不能承诺网络素材天然无版权风险。

用户已批准总体方案和 v2 视觉稿，实现按[实施计划](../plans/2026-10-28-implementation.md)推进。具体服务器访问、生产凭据与上线配置在具备可审查构建产物后补齐。
