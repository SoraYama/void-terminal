# 服务器定时更新原神数据

## 目标

由现有 Ubuntu 生产服务器每天北京时间 04:30 检查 AnimeGameData 与 genshin-db 的 main。任一提交有变化就固定两源提交，构建、校验并发布新数据。失败时保持或自动恢复原活动快照；用户关机、退出 Codex 或 Mac 断网均不影响。保留已发布快照及其文献、道具引用。更新任务不更新应用代码、不安装来自数据仓库的程序、不调用付费模型、不新增公网接口。

## 选择与边界

- 用户明确不使用这台 Mac。使用现有生产服务器上的 systemd 定时服务，不用本机 Codex 定时任务，也不增加付费构建机。
- 继续复制整库需要同时容纳旧库、新库和写入日志。现有整库约 34 GiB，服务器实测仅约 30 GiB 可用，整库复制不可用；增加构建机也不会增加线上磁盘。
- 仅构建一个独立 SQLite 快照。发布前将它封装为本机生成的只读 SquashFS 文件；历史快照不复制进新库，也不因新发布而删除。已有 `catalog.sqlite` 保留原位置，继续承载已有快照和运行期预算表。压缩包在知识服务内只读查询，无需每次解压。服务器已确认有 SquashFS、loop 设备、`mksquashfs` 和 systemd。单独验证挂载传播和重启恢复后才启用定时器。
- 首次可用的真实更新为主源 `d54f6f0d423ded9d055bb740a3e5f3aa8f2667f1`（2026-11-04 09:04 北京时间），镜像已匹配；补充源仍为 `49a6544a6c6ae36089cb42fa591fc46f01de8bcf`。执行时重新查两个头部提交，以该次查到的固定提交对作为构建输入。

## 获取与构建

1. 定时任务使用 `Persistent=true`，通过服务实例和主机文件锁避免重叠，支持手动触发。查询两源并与活动快照记录的提交对比较。无更新只记录检查结果，不下载语料、不重启服务。
2. 生成每次独立的来源清单：官方 commit 绑定 Git 根树，从验证过的目录树获取主源四个归档子树、四个 TextMap 和补充源目标文件的 Git blob 与大小。主源沿用固定 GitLab 镜像；检查镜像提交、归档范围，从解压文件的 Git blob 与权限重建子树，和官方子树哈希比对，再验证 TextMap blob。归档 SHA-256 用于本地缓存校验。补充源只取原有两语言五类正文及八份支持文件；按目录走树并校验内容，不接受截断递归树、路径越界或符号链接。仅来源清单驱动本次构建；应用代码中的旧基线不随日常发布改写。
3. 限制构建容器资源，优先保障线上。构建进程单独使用受限 CPU、内存、交换和超时，非 root 运行，只挂载自己的缓存/工作目录。压缩限一线程，低 I/O 优先级。仅在容量检查通过时开始，运行中持续监测，为现网预留 5 GiB，触线终止构建；中间文件仅属于本次任务，任务退出可清除，不删除已有发布与回退副本。先后清理不再使用的生成中间文件，以减少峰值占用。磁盘容量不足直接报失败并保留旧版。
4. 沿用归一化、物品校验、真实图片缓存和来源结构。一个新的离线 SQLite 文件只包含一个待发布快照，用适合临时建库的 DELETE 日志模式避免双份大 WAL；现网 SQLite 日志模式不变。快照 ID 绑定两源提交与归一化内容摘要。校验结束后才生成只读压缩镜像。

## 校验和发布

- 离线门槛：两源完整性清单一致、主源必要目录和语言齐全、归一化无新增解析错误。每语言文档与各物品类别不得出现较活动快照超过 5% 的下降，图片验证覆盖下降超过 5 个百分点也停在待查状态。确认 SQL 整库 `quick_check`、非空检索分块、装备/任务样本、道具来源和旧 ID 的取数，以及 `gameVersion:null`。镜像创建后验证只读挂载，数据库字节数和 SHA-256 须与通过验证的文件一致；无 SQLite WAL/SHM 依赖。
- `deploy/compose.catalog-refresh.yaml` 只为 knowledge 服务加入只读索引目录和 `/catalog-archives` 挂载，不更改 Web/Caddy 或公开 API。旧库仍是预算写入和未迁移历史数据的唯一位置。应用通过单份原子替换的注册表决定活动快照以及历史快照文件；按 `snapshotId` 路由，所有读取同一快照的道具和文献都来自同一 SQLite。新快照库以只读模式打开，不运行 schema 初始化。未知快照仍报原有错误；没有注册表的旧部署保持原行为。避免从请求数据拼接任意文件路径。
- 主机新目录 `/opt/void-terminal/catalog-refresh/{state,images,mounted,work}`；控制脚本及注册表由 root 管理，应用只读。通过专用共享挂载根和容器 `rslave` 传播只读子挂载；发布前确认当前容器确实能看到候选文件。开机恢复服务在 Docker 启动前根据已发布注册表恢复挂载，不改系统其他数据目录。活动镜像无法挂载时回退到最近可读版本，最终保底为现有库；只有历史镜像缺失时活动版照常服务，缺失的历史 ID 暂不可读并记录错误，不能返回另一版内容。挂载故障不全局阻断 Docker 启动。首次安装知识服务新镜像后先用旧活动快照验收，再接通自动发布。
- 发布前记录原活动注册表作为恢复日志。候选必须通过真实挂载与现有 knowledge 容器内私有探针读取验证，验收前不在公开 `snapshotId` 路由注册候选。使用构建时核对的不可变快照计数，避免每次状态请求扫描整库；代表性读请求必须在现有 Web 代理超时内完成。随后在一个原子写入中注册并切换活动指针。公网检查 `status`、道具列表/详情、文献检索和已保留的旧引用；失败则还原原注册表、撤销候选的公开路由并验证旧版。成功才提交运行结果并移除恢复日志。超时、信号、进程异常退出由服务退出后恢复钩子处理；主机重启时先恢复未确认的切换再挂载。保留曾被应用访问的快照文件，避免回退时破坏正在读的请求。
- 不自动清理已发布历史。空间门槛失败时记下所需与可用容量，留待运维扩容或明确批准的归档整理。`journalctl` 与本地运行结果能区分无更新、构建失败、回退和成功；不另发邮件或消息。

## 完成标准

1. 单测覆盖新/旧快照路由、来源树校验、无更新短路、容量不足、并发锁、发布失败恢复和中途终止恢复。现有服务回归通过。
2. 服务器实际验证定时表达式、独立目录、读权限、压缩快照挂载、Docker 可见性、恢复钩子。演练失败与重启恢复用独立目录和库，确认线上活动快照未变。
3. 执行一次真实检查；发现更新则按同一自动入口完成首次构建、验证和线上发布。确认两源版本、历史引用和新道具可读，复跑无更新直接结束。只有全部通过才启动周期任务。若上游校验或容量阻止发布，明确记录阻塞与旧版保留情况，不能以装好定时器冒充已验证自动同步。
