# 官网免费点数、项目赞助与防滥用改造方案

日期：2026-11-06。状态：用户已批准，进入实施。

已完成独立的可实施性审阅，未发现阻止制定实施计划的关键缺项；这不代表代码、风控效果或线上服务已验收。

## 1. 目标与已确定的范围

普通玩家使用官网时只需邮箱登录，不必了解模型供应商或申请 API Key。站长通过免费额度、风险控制与全站预算控制支出，赞助用于支持项目运行。

以用户最新指示为准：每日点数优先消耗，新人 20 点可以保存。此前“用完新人点数后才开始每日额度”的方案作废。

| 项目 | 规则 | 决策来源 |
| --- | --- | --- |
| 官网 AI 对话 | 必须登录；包括追问、重试、编辑后重发和图鉴发起的提问 | 用户要求 |
| 新人赠送 | 首次符合领取条件的账户获赠 20 点，长期保留 | 用户要求 |
| 每日点数 | 每日 3 点，优先消耗，剩余不累计 | 用户要求 |
| 首日总额 | 通过防滥用校验的新用户为每日 3 点 + 新人 20 点，共 23 点 | 上述规则的直接结果 |
| 重置时区 | 北京时间每天 00:00；英文界面注明 UTC+8 | 本方案建议 |
| 点数成本 | 沿用普通考据 1 点、深入考据 3 点 | 沿用当前代码 |
| 邮件申请 | 用户可以说明用途，站长人工决定是否赠送额外点数；不以赞助为条件 | 用户方向与本方案细化 |
| 赞助 | 国内外独立支持入口，赞助不产生点数或付费权益 | 本方案建议 |
| 设备识别 | 识别重复领取、批量注册等滥用，并提供误判申诉 | 用户要求 |
| 开源自部署版 | 默认 BYOK，无官网账户、免费点数、赞助、联系站长申请额度、设备采集流程 | 用户要求 |

资料浏览、原文阅读、图鉴浏览继续免登录。登录门槛发生在请求模型时，不挡住用户先认识网站。官网改为面向普通用户开放邮箱注册；原邀请名单仅保留为灰度发布配置，正式开放要等防滥用验收完成。

## 2. 现状与方案选择

当前代码已具备 hosted/self-hosted 两种模式、邮箱验证码登录、官网对话服务端登录校验、一次性 20 点赠送、普通/深入扣点、预占与释放、人工赠点及独立 SQLite 账本。账户面板目前突出可用、处理中、累计入账，并显示“充值尚未开放”。

主要缺口是：每日点数及其有效期、按来源分配扣点、设备风控与持久化限流、清晰的免费使用说明、赞助与联系入口。当前认证限流是 Web 进程内 Map，服务重启或多实例会使计数不完整。当前账户 summary/reserve 会创建账户并发新人赠点，必须调整，以免绕过新增领取校验。

采用现有账户面板扩展，加一个独立的“支持项目”面板。每日点数和长期赠点使用同一账本中的不同余额来源。与新建充值中心相比，这个方案符合免费使用的定位，也能复用现有认证和人工赠点工具。单一总余额无法正确表达每日清零和长期保留，因此不采用。

本轮暂停 Stripe/Paddle/Checkout 工作。现有未提交支付草稿保留并隔离，实施时从经核验的基线建立独立变更；不把工作区整包提交，也不启用支付路由或回调。历史账本和已有订单记录不删除。文档中未来 Stripe 接入的描述更新为已暂停。

## 3. UI 规划

### 3.1 视觉与布局

延续现有须弥场景、米白纸面、蓝灰正文、少量金色分隔线与现有字体。依据当前组件/CSS和仓库截图做结构规划；截图只是历史视觉参考，本方案尚无线上或新界面的浏览器验收。

桌面沿用居中账户弹窗；手机采用宽度贴近屏幕、可滚动的账户面板，主操作可见，邮箱键盘弹起后验证码和提交按钮可达。使用现有 Dialog 组件的焦点管理和关闭行为，不在面板内再叠加多层弹窗。

账户与支持入口置于侧栏底部；手机收在菜单内。对话下方已有操作保持紧凑，不插入大块赞助卡片；视觉较小的按钮仍保留适合触摸的点击区域。

### 3.2 页面和状态

| 位置 / 状态 | 展示 | 操作与反馈 |
| --- | --- | --- |
| 官网未登录 | 输入框下方轻提示“登录后提问，新用户可获赠 20 点，每日另有 3 点” | 可先写问题；发送时打开邮箱登录，成功后恢复本次草稿，由用户再次点击发送 |
| 登录面板 | 邮箱、验证码、领取规则与简短隐私说明 | 按风险结果展示人机验证；显示重发倒计时；移除“受邀邮箱”正式站文案 |
| 已登录侧栏 | “账户与点数”及当前可用总点数 | 点击查看组成，不把每日和永久储备混成无法解释的单一数字 |
| 输入框 | “本次 1 点”或“本次 3 点” | 余额不足时保留草稿；可改用普通考据，但不自动发送 |
| 新人状态 | 今日 3 / 3，储备 20；说明优先消耗每日点数 | 无需点击“领取”，登录和风控通过后自动入账 |
| 每日用完、有储备 | 今日 0 / 3，储备余额；提示接下来使用储备 | 正常继续提问，无打断弹窗 |
| 所有点数用完 | “今天的点数已用完，下次补充：北京时间 00:00” | 主动保留草稿；“邮件申请额外点数”与“浏览资料”可用；赞助不作为解锁操作 |
| 有点数被预占 | 可用余额与“处理中占用 N 点” | 不把预占当成已永久消耗；请求结束后刷新 |
| 全站预算耗尽 | “今日公共服务预算已用完，请稍后再来” | 明确个人剩余点数仍保留，不误报个人额度不足 |
| 设备风险 / 重复领取 | “免费点数领取需要进一步验证”或“此设备已领取过新人赠点” | 人机验证、重试时间、邮件说明共享设备的入口；不使用“作弊者”等指控性文案 |
| 账户服务异常 | 暂时无法读取点数，提供重试 | 不展示虚假的 0，不放行模型调用，不切换到 BYOK |

登录时只携带当前未发送的草稿；已存在的其他账户历史与草稿不迁移。登出、切换账户、登录失效时继续维持身份隔离。首次领取正在审核时，账户摘要明确区分“待验证”和“已领完”。

### 3.3 账户面板内容顺序

```text

邮箱地址                                登出

今日点数          3 / 3
每天北京时间 00:00 补至 3 点，未用完不累计

储备点数          20
新人赠点 20 · 额外获赠 0
每日点数优先，储备点数保留

普通考据 1 点 / 次 · 深入考据 3 点 / 次
[继续提问]   邮件申请额外点数

```

主区显示今日/储备两项，额外赠点为 0 时不展示多余明细。处理中的预占按来源展示在明细中。累计入账、模型及 token 信息放进可展开的使用记录，避免首页像财务报表。记录区仍能看到失败未扣点、每日过期、人工赠点及历史迁入。

手机使用纵向排列；中英文与暗色主题使用相同层级。下一次重置时间由服务端提供，前端倒计时只辅助展示；页面重新可见、跨过重置点、发送前和请求完成后刷新账户，不信任本地时钟计算余额。

### 3.4 支持项目

独立面板用简短文案解释用途：“虚空终端由个人维护。你的支持将帮助承担模型调用与服务器费用。赞助完全自愿，不影响免费点数，也不兑换额外额度。”

国内、海外各展示实际已配置的渠道；不按 IP 强制隐藏另一组。手机可展开保存二维码说明或打开平台页面。跨站跳转明确目标并保留当前问题。配置缺失的渠道完全隐藏，避免空按钮；没有可用渠道时，先发布免费点数功能，赞助入口暂不显示。

候选方案与上线条件：

| 渠道 | 本版接入方式 | 上线前核验 |
| --- | --- | --- |
| 国内：已有可用的微信赞赏 / 支付宝支持入口 | 展示站长提供的真实二维码或官方链接，不调用商户 API | 实际账户允许的使用场景、真实收款对象、二维码识别与提现能力；不能假设普通个人收款码适合所有线上用途 |
| 国内备选：爱发电 | 跳转纯支持用途的创作者页面 | 创作者账户、平台规则与实际提现验证；不设置点数兑换档位 |
| 海外：Ko-fi + 可收款的 PayPal | 跳转一次性支持页面 | 所属地区、账户类型、实际收款与提现；没有可用账户时暂不上线该入口 |

爱发电官方说明包含微信/支付宝支付及平台费用，但该帮助内容较旧，最终费率和账户准入以开户时后台与现行规则为准：[创作者 FAQ](https://guide.afdian.com/faq/faq-for-creators)。

Ko-fi 的资金直接经 PayPal/Stripe 收取，并不替站长提供一个独立结算账户：[Ko-fi 收款说明](https://help.ko-fi.com/hc/en-us/articles/115003980093-How-do-I-get-paid)。PayPal 现行大陆条款对 2026-06-30 后新注册个人账户的部分收款功能有额外限制，故此处仅列候选，不能承诺注册个人账户即可使用：[PayPal 用户协议](https://www.paypal.com/c2/legalhub/paypal/useragreement-full?locale.x=zh_C2)。大陆账户间转账也不宜作为国内方案：[PayPal 汇款说明](https://www.paypal.com/c2/cshelp/article/如何汇款？-help293)。

这是资金支持入口的设计，并非对内容授权、税务或渠道准入的确认。发布前只显示已核验可用的渠道，不将更名为“赞助”视为相关要求已解决。

### 3.5 邮件申请额外点数

入口同时位于账户面板与个人余额不足提示。文案：“如果你正在做较深入的考据，可以邮件说明用途，申请额外点数。”

使用配置的公开联系邮箱，通过 mailto 打开用户自己的邮件客户端，另提供复制邮箱与申请模板。模板包含账户识别码、申请用途、期望点数；不自动附带问题正文、聊天记录、设备指纹或凭据。明确用户自行发送，不创建站内自动发信或工单系统。

站长人工核对账户后使用现有幂等赠点工具发放，原因记录为人工支持调整；邮件或操作记录关联稳定的赠点引用，重试不重复发放。获赠点数进入储备，隔日不清除。对外不承诺必定获批或固定回复时间。

公开邮箱尚未确定；先用配置占位，不擅自把之前试用时提供的私人邮箱发布为联系方式。

## 4. 点数与账本规则

1. 每日余额上限 3，当天未用完的部分在北京时间 00:00 过期，新一天重新提供 3；不要求用户签到。长期离线后回来也只得到当天 3 点。
2. 长期储备包含新人、人工赠点与迁移保留的历史余额。本方案建议消耗顺序：每日 → 新人 → 其他储备；同类来源按入账先后。
3. 一次请求可跨来源扣点，例如深入考据 3 点，当日剩余 1 点，就占用每日 1 + 储备 2。余额合计足够即可，不要求某个来源单独凑够。
4. 发送时在服务端事务中按来源预占；完成才结算。失败、取消和超时按实际分配释放，重复回调幂等。预占本身不等于最终消耗。
5. 跨午夜仍结算原预占：昨天每日点数不挪到今天扣。昨天每日余额释放时只解除旧周期占用，不增加今天可用余额；储备部分照常退回。界面写明每日点数已随旧周期过期。
6. 每日记录具有账户 + 日期唯一约束。有效设备领取限制见下一节，也需唯一约束；并发登录、多个标签页、午夜瞬间刷新不多发。
7. 每次账户读取与请求准入检查服务端周期，采用事务性按需初始化；定时任务只做清理，不作为重置正确性的唯一依赖。读取不应绕过账户的领取资格校验。
8. 账本增加有效期、来源可用额、预占分配与周期状态；不能把 `total_granted` 每天覆写为 3，也不能简单每日向永久余额累加 3。历史累计量不参与直接余额推断。

## 5. 设备识别与滥用控制

### 5.1 信号与边界

本方案采用站内设备标识 + 低侵入浏览器特征 + 网络/行为风险 + 服务端预算。设备指纹不是物理设备的可靠身份证明，浏览器清理、伪造、隐私模式都可能绕过；目标是降低批量领取收益并限制最坏支出。

浏览器特征可形成可关联的识别信号，需控制采集范围与保留时间，参考 [W3C 隐私工作组指纹识别指导](https://www.w3.org/TR/fingerprinting-guidance/)。

- **稳定站内标识**：由服务端生成随机设备令牌，以 Secure、HttpOnly、SameSite 的第一方 Cookie 保存并验证；不信任客户端随意上报的 deviceId。令牌是浏览器实例标识，不能宣称等于一台物理设备。
- **辅助指纹**：浏览器/系统大类、语言、时区、屏幕尺寸分档等有限特征；版本升级或某一项变化不会直接视为新设备。作为相似性和风险信号，不作为硬唯一键。第一版不需要 Canvas、音频、字体列表等高熵采集。
- **网络与行为**：从已配置并清洗头部的可信反向代理取得 IP，结合验证码频率、新邮箱数量、设备切换、调用频率。不能信任来自公网客户端的任意 X-Forwarded-For，也不能仅凭同一 IP 封禁家庭/学校/移动网络用户。
- **存储**：服务端用独立密钥 HMAC 保存网络及指纹摘要、用途与密钥版本；原始辅助指纹不进入持久化业务库或日志。哈希仍可关联用户，隐私说明必须明确用途，不称为完全匿名。

拟定保留期：设备令牌与防重复领取标记最多 180 天；近期指纹/网络风险摘要和事件最多 30 天，到期删除。账户级已经领取的赠点记录随账本保留。设备 180 天窗口并非永久物理设备去重；不为延长去重保存无限期指纹。实际日志、备份清理也需覆盖这些数据。

### 5.2 自动领取策略（本方案建议，可配置）

| 情况 | 处理 |
| --- | --- |
| 首次正常邮箱 + 新设备 | 完成邮箱验证与必要的人机验证后自动发每日 3 + 新人 20 |
| 同一账户换设备 / 重复登录 | 账户级幂等，不补发新人奖励或当天每日额度 |
| 同一有效设备令牌下换新账户 | 180 天内只允许自动领取一次新人 20；其他账户可登录，但新人赠点待人工核实，不静默吞掉领取资格 |
| 同一有效设备令牌下多个账户领取当天 3 点 | 默认只为一个账户自动发放当天 3 点；已经合法入账的储备保留。共用设备可以邮件申请分别授权，授权有审计记录 |
| 只有辅助指纹相似 / 同 IP | 提高风险分，不仅凭这一项拒绝赠点；需要时要求人机验证或进入短暂冷却 |
| 批量注册、换设备、验证码爆破 | 按邮箱/设备/IP组合持久化限流；限制新增赠点和模型调用，显示可重试时间或人工处理入口 |
| 标识缺失、Cookie 被禁用、隐私浏览器 | 不直接判定作弊；走验证或人工领取通道，避免无设备凭据就自动发赠点 |
| 风控服务故障 | 新赠点发放停止并显示暂不可用，禁止绕过；模型调用必须完成现有账户与预算准入校验 |

设备限制是自动领取防线，不能没收旧账户储备或让一人更换设备重复领点。每次发放同时校验账户唯一键和服务端设备资格；领取失败保持可重试/可人工批准的状态。风控采集和检查覆盖首次领取、每日首次补充及模型准入，不能只在前端登录框执行。

验证码建议保留当前每邮箱 15 分钟 3 次发送、8 次验证的上限，并增加 60 秒重发间隔；IP/设备的新账户和调用阈值通过配置管理，先灰度观察共享网络误判。限流改为共享的持久化存储，原子更新且能跨服务重启生效；沿用当前单实例 SQLite 架构，不为第一版引入 Redis 依赖。

人机验证推荐接入可替换的服务适配层，首选验证 Turnstile 在目标大陆/海外网络的可达性；不可达时保留明确重试和邮件处理，不因校验失败直接允许领取。必须服务端校验短期、单次使用的 token，并校验预期站点和用途：[Turnstile 官方验证文档](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/)。无论人机验证是否通过，账户与设备的重复领取约束都生效。

身份与风控分离：即使用户绕过网站表单直接完成身份服务登录，也不能绕过官网后台领取资格；账户摘要、内部开户和 reserve 路径不能自行补发奖励。手工赠点与风控豁免是两个独立的授权操作，不能赠点一次就永久豁免风控。

梳理所有能触发运营方模型费用的路径，包括模型连接测试；若官网仍保留真实模型测试，必须同样受登录、风控及公共预算约束，不能成为免费调用旁路。

### 5.3 控制总成本

保留每账户单个活跃请求、每次模型上下文/输出与 Agent 轮数上限、全站 token 预算，并增加按日/月的运营预算闸门和监控。点数不是固定 token 数，因此不能仅靠每日 3 点承诺费用封顶。

运营预算数值在实施前根据可承担支出配置；未配置时不开放无限公共调用。金额预算按版本化模型价格和每请求最坏 token 用量预占，价格变化需复核，实际供应商账单另行对账。供应商账户提供的余额/用量限制作为补充，不宣称本地估算等同绝对账单上限。

## 7. 存量迁移与回滚

旧账本无来源级消耗分配，不能推测某个旧请求用了新人还是人工点数。采用保守策略：升级前已完成和预占记录完整保留；旧剩余权益整体迁入长期“历史储备”，不补发一次新人 20；升级当天单独提供符合条件的每日 3 点。旧预占明确绑定历史储备，后续完成或释放不能重复计入余额。

迁移前后逐账户核对已消耗、仍预占和长期可用总额一致；旧支付记录若存在也保留，不因暂停接入而丢失。旧账户首次新登录建立设备标识，历史奖励不追溯按设备撤销。

先停止账户写入、备份并验证，再迁移演练；部署时核验挂载的是原账本。迁移后的新格式由新版备份/验证工具覆盖。产生新写入后不能仅回滚程序并恢复旧备份，否则会丢赠点与扣点；优先修复前进，必要时停写后对账恢复。

## 8. 必须验收的场景

- 新账户首日 23 点；连续使用先扣当日 3，储备20保持；普通1/深入3与跨来源组合正确。
- 多次登录、多标签页、请求重放、新设备访问不重复发新人或每日点数。
- 00:00、离线多天、伪造客户端时钟、午夜并发、昨日请求今日完成/失败，均不超发或误扣储备。
- 失败、取消、预占超时、重复/延迟结算；现有晚结算限制不被掩盖，调用预算仍受约束。
- 旧账户仅有试用、混有人工赠点、历史余额、在途请求、零余额及异常账本的迁移和恢复。
- 同设备换邮箱、清理 Cookie、辅助指纹碰撞、共享 NAT/家庭设备、隐私浏览器、伪造代理头、风险接口故障和人机验证重放。
- 直接调用账户/对话 API、直接身份登录、绕过 JS、缺设备信号仍不能绕过服务端准入。
- 正常用户被误判时有可执行的人工处理路径，人工批准可审计；已入账储备不被无故清除。
- 375/390 像素手机、桌面、浅深色、中英文、键盘与读屏；长邮箱、输入法、验证码粘贴、关闭面板后焦点回位。
- 官网无 BYOK 回退；自部署不调用账户/风控服务、不显示点数/赞助/邮件申请，无相关服务凭据也可正常 BYOK。
- 赞助链接、真实二维码、同一手机识别流程、公开收款信息和联系邮箱逐项验收；未配置项不出现。
